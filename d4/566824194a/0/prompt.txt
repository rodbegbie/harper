#### Minor (Nice to Have)

1. **`Mask::from_iter` panics on overlap; the combined-span collect relies on YAML grammar never nesting a comment inside a scalar.** `YamlMasker::create_mask` does `spans.into_iter().collect()`, and `FromIterator for Mask` (`harper-core/src/mask/mod.rs:34`) *asserts* `a.end &lt;= b.start` — it panics rather than degrades if any comment span and scalar span overlap. This is safe in practice: YAML block scalars swallow `#` as literal content (so no comment node forms inside them) and trailing comments are always whitespace-separated from the preceding scalar. So overlap is structurally impossible for well-formed YAML, and this is a *language-server* code path where a panic on a user's file would be worse than in a test. There's no explicit test proving a `#`-bearing block-scalar line doesn't produce an overlapping comment node. Consider either a defensive `merge_whitespace_sep`/dedup instead of asserting `collect`, or a one-line fixture with `notes: |` containing a `# ...` line to lock the grammar's behavior in.

2. **`filtered_values.yaml` doesn't exercise the URL/path/version/identifier heuristics end-to-end.** Every value in that fixture is a *single* whitespace-token (`enabled`, `production-ready-config`, `2.10.4`, `https://…`), so the `word_count &gt;= 3` gate rejects them all before the URL/semver/identifier predicates ever run. The predicates *are* covered at the unit level in `yaml_heuristics.rs` (e.g. `please upgrade to 1.2.3 today now`), so this is a fixture-strength nit, not a coverage hole — but the end-to-end file gives a false sense that it's testing those specific rejections.

3. **Dead sub-condition in `looks_url_path_or_version`.** `(word.contains('/') || word.contains('\\')) &amp;&amp; !word.contains(' ')` — `word` comes from `split_whitespace()` and can never contain a space, so `!word.contains(' ')` is always true. Harmless, but confusing to a future reader; drop it.

4. **No end-to-end fixture for multi-line prose in sequences or deeply nested mappings.** `clean.yaml`'s sequence items are all 1-word kebab values, so a *prose* sequence item is never masked in a fixture. Low risk (unit tests cover the heuristic; the masker is structure-agnostic), just an untested shape.

5. **Two separate `impl YamlMasker` blocks** (one for `new`/`create_ident_dict`, one for the node predicates). Purely cosmetic.

### Recommendations

- Ship it. Optionally fold Minor #1 (a block-scalar-with-`#` fixture) and #3 (dead condition) into a quick follow-up commit — #1 is the only one with any robustness value.
- The **known anchored/explicit-key limitation** is accurately characterized as narrow. Anchors in config YAML overwhelmingly attach to *values* or whole mappings (`&lt;&lt;: *defaults`), not to keys; `&amp;anchor key: value` and explicit `? key` syntax are rare in the config/CI/deployment YAML this feature targets. The failure mode is also benign: a span-merge bleeds a key name into an adjacent value's lint span, producing a possibly-spurious lint or slightly-off underline — *not* a panic and *not* silent data loss. The prior triage (non-blocking, documented follow-up) is correct. I'd only ask that the limitation be recorded in a code comment on `is_mapping_key` (it partly is) or an issue, so it isn't rediscovered from scratch.
