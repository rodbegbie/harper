**1. `/Users/rod/build/harper/packages/lint-framework/src/lint/LintFramework.ts:208` — high-ish/medium: a rejected lint pass silently drops the coalesced follow-up.**

The dirty check sits *after* the `try/finally`, so when the `Promise.all` rejects the `finally` clears `lintRequested` and the exception propagates straight out of `requestLintUpdate` — line 208-211 never runs. Scenario: the user is typing while a lint is in flight (`lintDirty = true`), the provider rejects (in MV3 this is routine — service worker recycled, "message port closed"), the guard is correctly released but the queued re-lint is never issued, so highlights stay stale against the old prefix until the 1-second self-poll or the next keystroke. The PR body flags the `update()` → `requestLintUpdate()` unhandled rejection as pre-existing and out of scope, but this line introduces a *new* one on the same footing. If the follow-up pass rejects, it surfaces as an unhandled rejection in every real browser, not only under test. **3. `/Users/rod/build/harper/packages/lint-framework/src/lint/LintFramework.test.ts:26` — medium: the test's validity rests on `requestAnimationFrame` running at ~60 Hz, which is not guaranteed.**
